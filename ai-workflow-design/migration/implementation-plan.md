# Поэтапное внедрение

План предназначен для последующей отдельной задачи. Этот пакет не устанавливает скиллы, не перезаписывает system prompts и не изменяет проекты. Оригинальные промпты не нужны для проектирования или начала compatibility assessment.

## Обязательные и опциональные изменения

| Обязательно для заявленных гарантий | Опционально / после пилота |
|---|---|
| Control-only Orchestrator с реальными tool restrictions | Несколько моделей на разные профили |
| Раздельные роли/контексты Test, Developer, Reviewer | Автоматический model fallback после измерения качества |
| Scoped filesystem и isolated build runner | IDE MCP при доказанной безопасности |
| OpenSpec как канонические требования, минимальный design contract | Git history analysis для сложных исследований |
| Test lock до бизнес-логики, behavioral Red для нового поведения | Автоматический reuse research по dependency map |
| Trustworthy evidence и exact-snapshot gates | Подробные dashboards затрат/latency |
| Scala Skill и Scalafmt для затронутого Scala-кода | Property-based тесты при наличии подходящего стека |
| Компактные outputs, bounded retries и эскалации | Автоматизация shared workspace operations вместо ручной |
| Independent review, permission acceptance, rollback | Отдельные расширенные deep-dive walkthrough |
| Доступный по запросу Change Walkthrough | Автоархивация OpenSpec только отдельной согласованной задачей |

## Этап 0 — снимок и совместимость, без замены ролей

Владелец внедрения фиксирует текущие workflow inputs/outputs, рабочие task templates, доступные APIs/tools, команды CI, версии OpenSpec/Scala, реальные пути, model endpoints и security constraints. Если конфиги доступны в разрешённой области — read-only анализ. Если нет — не требовать оригинальные prompts; использовать наблюдаемое поведение и описанные интерфейсы.

Сохранить разрешённый rollback snapshot текущих настроек или инструкции ручного восстановления. Не копировать секреты в артефакты. Результат: compatibility map «нынешний интерфейс → новый контракт», список неподдерживаемых capabilities, выбранный strict/limited pilot mode. Выход: все null/empty значения profile либо заполнены обоснованно, либо запуск strict явно заблокирован.

## Этап 1 — технические границы и контракты

Администратор/runtime owner создаёт identities, инструменты allowlist, scoped overlays, publisher, runner и artifact/state adapters, используя существующую инфраструктуру. Внедрить result schema и byte limits; проверять hashes, producers, timestamps, test selection и phase transitions. Сначала выполнить P01–P22 в disposable репозитории. Если shared account/shell обходит права, strict не допускается.

Выход: prevention проверен по эффектам, audit сохраняется, Orchestrator не может читать source/body или выдавать grants. Независимые services не доверяют self-reported success.

## Этап 2 — prompts и skills в тестовом профиле

Собрать каждый prompt как common + role, установить skills в тестовый каталог, привязать роль к минимальной capability. Убедиться, что full-parent transcript не наследуется. Настроить explicit-only walkthrough и natural-language routing. Никакого копирования новых инструкций поверх неизвестных старых prompts: создать отдельную именованную версию профиля и переключаемую ссылку.

Провести сценарии 1–7 на небольшой копии проекта: ветви с отсутствующим API, failed formatter, test defect, review return и stale receipts обязательны. Измерить schema validity, evidence truthfulness, токены, latency и количество ручных вмешательств.

## Этап 3 — shadow без конкурирующих записей

На одних и тех же обезличенных задачах сравнить новый профиль с доступным baseline. Старый workflow может дать принятую человеком реализацию, новый — только свои изолированные artifacts; они не пишут в один рабочий каталог. Если старый workflow недоступен, сравнивать с задачами и ожидаемыми исходами, проверенными разработчиком, не заявляя сравнительное превосходство.

Проверить false-positive findings, независимость test oracles, completeness, архитектурную экономность и качество walkthrough. Критерии перехода: ноль ложных passes/обходов прав, все mandatory gates подтверждаются; продуктовые показатели не хуже заранее выбранного baseline в пределах согласованных порогов.

## Этап 4 — ограниченный canary

Переключить небольшой класс задач (например локальные изменения без схем БД/новой конкурентности) на новый именованный профиль. Review и финальное принятие человеком остаются. Сначала заменить контрольный слой и контракты; затем связку Test/Developer/Reviewer включать целиком, чтобы не создать ложную независимость из несовместимых форматов. Research/Spec/Architect подключаются через validated refs; Planner заменяется Architect+tasks.

Operator автоматизировать лишь для операций, которые уже прошли permission tests. До этого shared integration может выполнять человек. Принцип test-first не ослабляется ради скорости. Результат — несколько задач с воспроизводимой provenance и подтверждённым откатом.

## Этап 5 — расширение

Постепенно добавлять более сложные модули, reuse-cache и model routing после измерения результатов. При каждой смене tools, model endpoint, sandbox или версии адаптера повторять затронутые acceptance checks. Не менять одновременно права, модель, формат контрактов и архитектурную политику без отдельной причины: будет трудно определить источник регрессии.

## Откат

Триггеры: запись вне scope, ложный pass, утечка контекста в preimplementation tests/reviewer, повторяемая потеря artifact refs, невоспроизводимые проверки или превышение согласованного уровня ошибок. Остановить выдачу новых задач новому профилю, отозвать его capabilities, сохранить immutable evidence и незавершённые bundles. Вернуть dispatcher pointer на предыдущую проверенную версию или ручной процесс. Не reset/delete пользовательские изменения и не переносить непроверенные patches автоматически.

Для незавершённых задач зафиксировать last_valid_state, актуальные snapshots, открытые вопросы и владельца. Продолжение через старую систему требует повторной проверки входов и прав; уже существующий JSON success не переносит доверие между runtime автоматически.

## Замена без оригинальных prompts

Опираться на внешние контракты, а не на предполагаемый текст старых инструкций. Для каждой роли подготовить adapter входов/выходов, провести контрольную задачу и явное переключение профиля. Если неизвестны скрытые side effects старой роли, сначала разрешить только read-only shadow. Архивировать старые конфиги можно только если они доступны и это отдельно разрешено; их отсутствие не препятствует использованию новых самостоятельных prompts.
